# Jury Presentation Preparation

## When to use
Before a crit, review or the final jury.

## Required inputs
`docs/project-state/PROJECT-STATE.md`; output of `academic-rubric-alignment`; Q8 decision (demo format); the real build status.

## Procedure
1. **Claims audit first:** list every claim you plan to make, labelled Implemented (evidence) / Designed / Proposed / Assumption. Drop or relabel anything unsupported.
2. **Structure** (suggested, adjust to the brief): problem → concept and fiction → core loop → five missions → design principles (consent, honesty, safety) → map approach → UI and art direction → build and test status → process and decisions (incl. D17–D19) → what's next.
3. **Demo plan:** the real app in the phone viewport centred in a MacBook browser (D18). Script one mission end-to-end, timer pause and resume, and the token award. Pre-check the device, browser, network and storage. Never present a mockup as the working game.
4. **Fallback:** if the live demo fails, use a recorded walkthrough of the **real** app, clearly labelled as recorded.
5. **Jury Q&A:** at least 12 likely questions with honest answers. Include: How do you verify physical tasks? Why no GPS? Is the map accurate? What about privacy? What if no one wants to talk to you? Why 15 minutes? What did playtesting show? (If there was none, say so.) What isn't built?
6. **Timing:** rehearse against the time limit from the brief (if known).

## Validation checklist
- [ ] Every slide claim traced to evidence or labelled
- [ ] Demo uses the real app only
- [ ] Hard questions included with honest answers

## Failure cases
Build not ready (present the design honestly as design; no fake demo); brief unknown (structure is provisional).

## Ask for clarification when
Demo format (Q8), time limit or audience is unknown.

## Completion report
Return: what was checked, results with citations, files changed (or none), commands run with their actual output, items `NOT RUN` and why, open questions raised.
